# Screen recording (Cap / ffmpeg) and past recordings

Screen recording (Cap): if Cap is set up on this machine (cap.so -- a one-time install, see config.py's CAP_ENABLED comment for the exact steps), drive its CLI via Bash for anything meant to be shared, posted, or kept -- not just a throwaway clip. Run `cap doctor --json` first if you've never confirmed this session's machine is capture-ready, and `cap targets --json` if you need to pick a specific screen/window rather than the default (its `id` feeds back into record). For a known, fixed length: `cap record start --duration <seconds> --json` (ask the user how long, default 15-30s if they don't say) runs in the foreground, blocks until done, and emits a `started` event then a `stopped` event once it's actually finished -- treat that as the recording being complete. For an open-ended recording where you don't know the length up front, add `--detach` instead -- it returns immediately with a `recordingId` and keeps recording in the background; check on it with `cap record status --json` and end it with `cap record stop --json` (passing that recordingId) once told to stop. Either way, Cap keeps processing afterward (transcription, AI summary) -- run `cap caps wait <id> --for all --json` before treating it as ready to use elsewhere. Found live: `--for all` can genuinely sit there for a very long time if even ONE of the artifacts it's waiting on (transcript, AI summary) is stuck or unavailable server-side for that particular recording -- if you have a specific artifact you actually need, wait for just that one (check `cap guide --json` for the exact flag) rather than `--for all`, so one stuck extra doesn't block something that's already ready. Either way this is now backstopped: a `cap` call blocking past config.TURN_MAX_DURATION_SECONDS (20 minutes) gets the whole conversation reset and the stuck `cap` process killed outright (see backend/process_watchdog.py) rather than left running indefinitely, so you can tell the user honestly it won't hang forever even if it does need a retry. To get a plain video file from the finished `.cap` project, `cap export --json` renders it (this one streams NDJSON progress events in a different shape than other commands -- PascalCase `type` tags, not the usual camelCase); to get something shareable instead, `cap upload <path> --json` returns a link directly, project or exported file either one. Every Cap CLI command returns JSON on stdout with `--json` -- parse that, don't screen-scrape human-readable text. Run `cap guide --json` any time you're unsure of the exact current command/flag surface -- it's Cap's own live self-description and is authoritative over anything you think you remember about it. Never type a password, CAP_AGENT_TOKEN, API key, or any other secret Cap's CLI asks for into chat or a command yourself -- that's what `cap auth login` / `cap caps unlock` are for, and Cap's own docs are explicit that agents should never handle those directly.

Cap's recordings library: once Cap is set up, you also have read-only tools (via its MCP server, not the CLI) for working with recordings already in the Cap library -- finding one by title, pulling up its metadata/URLs, and reading its full transcript or AI summary. Reach for these instead of re-processing a raw video file whenever the user asks about something they already recorded ("what did I actually say in yesterday's demo," "find my last recording about X") -- it's already transcribed and summarized, no re-watching required.
